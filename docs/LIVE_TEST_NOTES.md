# Notes on the Live test (2026-11-22)

Companion to [LIVE_TEST_PROTOCOL.md](LIVE_TEST_PROTOCOL.md), which is generated by
`tests/live_protocol.py`. This file records how the test was set up, what was
checked by hand in addition, what the test found, and what it did not cover.

## Setup

- Windows 11, Ableton Live 12.3.6 Suite (built-in Python 3.11.6), German UI.
- The Remote Script was installed with `scripts/install_remote_script.ps1`
  (the previous installation was moved to a backup folder and put back with
  `-Restore` after the test).
- Throwaway Set: a copy of Live's default Set, saved once under a new name by
  Live 12 inside a Project folder (see finding 4).
- The MCP server ran as a child process of the test script; all 79 tools were
  called through the MCP protocol. 146 calls, all passed in the final run
  (bridge 2.1.0 with the safety layer; the run before it, bridge 2.0.0 without the
  safety layer, had 76 tools and 109 calls, all passed).

## What the test found (and what was changed because of it)

1. **Live applies some setters one display tick late.** Reading
   `current_song_time`, `loop`, `record_mode` or `is_playing` right after
   setting them returns the old value. Handlers can now return `Later(...)`;
   the hub reads the result back on the next tick. Locator commands, which
   need "move the play position, then toggle", run as a sequence over
   several ticks.
2. **Live's built-in Python has no `ctypes`.** A Remote Script therefore
   cannot type shortcuts. Saving (Ctrl+S) and grouping (Ctrl+G) are done by
   the MCP server process instead, which brings Live's window forward first
   and refuses to type if Live is not in front or shows a dialog.
3. **`import numpy` blocks forever inside an MCP server on stdio (Windows).**
   It hangs when another thread is reading the process's stdin pipe.
   `normalize_clip` measures the file peak without numpy for that reason.
4. **Live refuses a plain save in two situations** and opens a dialog
   instead: the Set is not inside a Project folder, or it was created by an
   older Live version. `snapshot_session` reports the dialog instead of
   claiming a save.
5. **Shift+arrow in the Session grid selects clip slots, not tracks.** The
   grouping shortcut first moves the cursor up to the track title.
6. **A track that is the last one inside a group cannot be deleted** through
   the API (`RuntimeError: Couldn't delete track`); deleting the group works.
7. Live's own warp marker calls (`add_warp_marker`, `move_warp_marker`,
   `remove_warp_marker`, `Live.Clip.WarpMarker`) work in 12.3.6.

## Track levels and Y Meter (2026-11-23, bridge 2.2.0)

Run by hand against a throwaway Set in Live 12.3.6 (Wavetable chord clip playing on one
track), not by `tests/live_protocol.py`:

- `get_track_meters` read every track, both return tracks and the main track; MIDI tracks
  without an instrument report no audio output. Live's display tick ran at about 5 per
  second (2 s gave 10 to 11 readings), so the window is timed by the clock, not by
  counting ticks.
- **Y Meter** (`m4l/Y Meter.amxd`) loaded from the User Library on a track and on the
  main track, passed the audio and sent `/ytrack` frames five times a second; the track
  name arrives in quotes when it contains spaces (the server strips them).
- **Meter scale.** Fader of the chord track stepped from 0 to -40 dB with Y Meter
  pre-fader as reference (expected post-fader peak = Y Meter peak + fader):

  | Expected peak (dBFS) | -12.7 | -15.7 | -18.6 | -24.6 | -30.6 | -36.6 | -42.7 | -52.6 |
  |---|---|---|---|---|---|---|---|---|
  | Live meter reading | 0.751 | 0.709 | 0.652 | 0.588 | 0.487 | 0.439 | 0.356 | 0.228 |

  Least squares: `meter = 0.01292 * dB + 0.9043` (residuals up to 1.7 dB). Live's meter
  is linear in dB, reaches 1.0 at about +7 dB and 0 at about -70 dB. The earlier
  conversion in `get_master_levels` (`20 * log10(meter)`) was wrong and now uses this
  calibration. Cross-check: the chord track at -20 dB fader read -32.0 dB on Live's
  meter while a Y Meter on the main track measured -33.3 dBFS.
- Not covered: peaks above -12 dBFS (the calibration is extrapolated there), stereo
  material panned hard to one side, and the WASAPI analyzer at the same time.
- Several MCP servers were running on the test machine and all listened on UDP 7878;
  Windows delivered each datagram to one of them. The test used a Y Meter built for
  port 7879 (`build_y_meter.py --port 7879`).

## Not tested

- **macOS**, and any Live version other than 12.3.6.
- **Real analyzer data.** `apply_mastering_corrections`, `suggest_mastering_chain`,
  `color_track_by_spectrum` and `color_all_tracks_by_spectrum` were fed one synthetic
  UDP frame by the test. `analyzer/audio_analyzer.py`, the dashboard and the Windows
  service wrapper were not run (Y Meter was, see above).
- **Audible output.** Nothing was checked by ear; the master meter was read
  once while a silent Set was playing.
- **Loading third-party plug-ins.** `search_vst` listed installed plug-ins;
  none was loaded (the bridge command `load_vst_plugin` was not called).
- **Bridge commands without an MCP tool**: `rebuild_locators`,
  `repair_arrangement_warp`, `set_tempo_follow`, `get_tempo_follow`,
  `get_arrangement_midi_notes`, `replace_arrangement_clip_notes`,
  `get_browser_item`, `get_browser_items`, `get_browser_categories`,
  `probe_warp_api`, `delete_track` (used for cleanup only), `eval_code`
  (used once for exploration with the switch file present; refused without it
  in the offline tests). Most of them run in the offline tests against the
  fake object model, not against Live.
- **Warp operations that move markers** (`warp_intel` with `drag_to_grid`,
  `nudge`, `quantize_region`, `anchor_and_move`): only `analyze_drift` ran in
  Live.
- **Single-step undo for the other kinds of steps**: mute, colour, send, return
  fader, clip name, clip gain, scene tempo, loop brace, EQ mode, device parameter,
  sidechain routing, warp mode, new clip, new arrangement audio clip, deleted or
  cleared locators. They use the same mechanism and run in the offline tests in
  part, but were not taken back in Live.
- **Journal across loading another Set** in the same Live session, and the limit
  `ABLETON_MCP_MAX_ZONE` in Live (offline test only).
- **Freezing**: Live's API has no call for it; `freeze_track` only reports.
- **`tools/melody_check/`**: adapted to the new note format, not run.
- **Long sessions and load**: no test over hours, no large Sets, no second
  client connected at the same time (for example a hardware controller
  script on another port).
- **Old MCP server against the new Remote Script** (mixed operation): not tried.
